# 身份信息与放行决策

本次调整只涉及后端请求处理，不改变 HTTP 路径、前端表单或数据库结构。

## 一次请求怎样经过这些代码

1. `MallApiServer.handle` 取得 Authorization 请求头。
2. `RequestAuthentication.resolve` 解析 Bearer 格式，调用 `SessionStore.find` 查找未过期的会话，返回身份结果。
3. 统一入口依据 `requiresLogin(path)` 判断该路径是否要求登录。如果需要登录且结果中没有有效会话，入口返回 HTTP 401。
4. 路由把结果中的当前用户交给 Service。管理员角色、账号当前状态、资源归属等业务判断仍由既有 Service/DAO 执行。
5. 业务结果或错误由统一入口转换成 HTTP 响应。

`resolve` 和 `find` 只报告身份结果。缺少、伪造或过期的凭证会得到空身份，不会由这两个方法发送响应或决定业务是否允许执行。

## 哪些路径公开

仅 `/api/health`、`/api/auth/login`、`/api/auth/register` 不要求已有登录会话。
其他 `/api/` 路径默认要求登录，包含将来新增的业务路径。接口自己的 HTTP 方法、输入字段和业务权限检查继续执行。

## 三类不同的决策

- 身份事实：有效会话对应哪个用户。来自后端会话，忽略客户端自报的角色。会话中的角色是登录时的信息。
- 入口规则：这个路径是否必须先登录。由统一入口的公开路径清单定义。
- 业务权限：这个用户此刻能否进行这项操作。既有业务会读取当前账号状态/角色，并检查操作对象。有效会话本身不表示可以执行管理员操作。

身份结果通过方法参数传递，仅属于当前请求，没有放入共享的“当前用户”变量。

## 与原先规则方法写法的区别

`resolve(...)` 返回结果，让调用者判断；`requireAdministrator(...)` 表达调用者已经选择的管理员规则，失败时抛异常。这是两种职责安排。此次按返回结果的方式拆分身份解析，既有业务权限方法未作批量重构。

本次验证应覆盖无凭证/伪造凭证、会话过期、退出登录、公开路径边界，以及不同用户同时请求时身份互不混用。
