## 1. 编写目的与依据

本说明书规定运动装备商城应实现的业务、数据、技术约束及验收方法，作为后续数据库设计、Java 开发与测试的依据。需求基线描述目标能力，不表示这些能力已经全部实现。

主要依据为老师下发的《项目011_运动装备商城.docx》（V1.0，2026-10-15），重点对应其第三节数据设计、第四节功能与技术要求、第五节 Git 管理、第六节工程结构和第九节交付物。

文中的“课程明确要求”来自上述要求书；“本工程约定”是为使业务可执行而补充的设计选择，两者分别列明。商品增加单价及订单保留历史成交金额，已由项目开发者于 2026-10-27 确认。

源码仓库：https://gitee.com/Nisegitee/sports-mall

当前实现基线为软件0.2.3。已有独立Swing客户端、HTTP后端、五张MySQL表与四个MongoDB集合，完成注册登录、本人电话与档案维护、订单创建筛选取消、评论发表读取、三条聚合、两个视图和两个过程。管理员维护、完整CRUD、分页、数据配额及最终测评仍待完成，逐项状态见《需求对照与进度》。

## 2. 项目范围与使用者

### 2.1 业务范围

课程明确要求覆盖用户管理、树形分类、商品基础与详情、浏览行为、订单、评论、日志和统计报表，并通过 MySQL 与 MongoDB 协同存储和查询体现两类数据库的分工。

本工程首版订单按“一单购买一件商品”处理。先完成课程列明的业务，不增加购物车、多商品订单、库存管理、外部支付或物流接口。界面形式不是原文硬性指标，当前命令行入口继续保留；最终应能操作和演示完整功能。

### 2.2 角色与权限

课程明确设置 ADMIN、USER 两类角色并要求权限管理。以下逐项权限为本工程约定，权限在业务服务中校验，不能只靠隐藏菜单。

| 操作范围 | 普通用户 USER | 管理员 ADMIN |
|---|---|---|
| 浏览、筛选商品与查看详情 | 可以 | 可以 |
| 修改用户信息、维护档案 | 仅本人 | 可管理账号状态，档案按管理权限访问 |
| 分类、商品录入和维护 | 不可以 | 可以 |
| 创建与查询订单 | 创建并查询本人订单 | 查询全部订单、处理订单状态 |
| 评论维护 | 发表、修改和删除本人评论 | 查询及管理评论 |
| 统计、系统日志与日志导入 | 查看本人活动报告 | 查看管理统计及系统日志，执行导入 |

注册默认创建 USER，不能通过注册输入直接获得 ADMIN。账号停用后不得继续执行需要登录权限的操作。

## 3. 功能需求与可观察结果

下表的业务模块来自课程要求；具体校验与权限按第四节工程约定执行。每项功能均须通过真实数据操作展示结果，而不是仅声明类名或依赖。

| 编号 | 功能及输入 | 必须产生的结果 |
|---|---|---|
| FR-01 | 注册：用户名、密码、邮箱等 | MySQL 保存用户；密码为哈希；重复用户名或邮箱得到明确提示 |
| FR-02 | 登录：用户名、密码 | 验证密码及账号状态；返回当前角色；MongoDB 记录登录结果 |
| FR-03 | 信息与档案：联系方式、姓名、地址、备注等 | 更新对应用户或档案；重新读取可见修改结果；普通用户仅操作本人 |
| FR-04 | 角色权限：当前账号、待执行操作 | 普通用户不能执行管理员维护操作；越权请求无数据改动 |
| FR-05 | 分类：名称、上级分类、维护动作 | 保存并显示树形分类；维护分类及上下级关系；防止循环引用 |
| FR-06 | 商品维护：名称、分类、单价、状态、描述、图片和扩展属性 | MySQL 保存基础信息，MongoDB 保存详情，通过同一商品编号关联；支持新增、读取、修改、删除 |
| FR-07 | 商品查询：关键词、分类、状态、价格条件、页码和每页数量 | 返回符合组合条件的分页商品及详情；同一条件下排序稳定；无匹配时返回空结果 |
| FR-08 | 浏览行为：当前用户、商品、访问事件及客户端信息 | MongoDB action_logs 写入行为记录；后续统计可查询到该行为 |
| FR-09 | 下单：当前用户、商品编号 | 校验用户和商品可用性；读取商品单价，保存一笔订单；MySQL 相关改动整体成功或回滚 |
| FR-10 | 订单查询：状态、起止时间及当前用户 | 返回权限范围内的订单；按状态和时间筛选；显示订单保存的历史金额 |
| FR-11 | 订单处理：订单编号、目标状态 | 按允许的状态转换修改；非法转换或越权时保持原状；记录操作结果 |
| FR-12 | 评论维护：商品、评分、文字、标签 | MongoDB comments 支持新增、读取、修改、删除；校验评分范围与操作权限 |
| FR-13 | 评论统计：商品编号等条件 | MongoDB 聚合返回评论数、平均评分等可核对结果 |
| FR-14 | 热门排行：时间范围、结果数量 | MongoDB 聚合按浏览次数降序排行；并列时比较累计停留时间，再按商品编号稳定排序 |
| FR-15 | 用户活动报告：用户及时间范围 | MongoDB 聚合返回该用户活动次数、行为类型分布等统计；普通用户仅查本人 |
| FR-16 | 月度报表：年份、月份 | 调用 MySQL 存储过程，返回月度订单数量和已完成订单金额等汇总 |
| FR-17 | 日志查询与导入：筛选条件、导入数据 | MongoDB 查询系统与行为日志；导入应报告结果，JDBC 批处理相关原文歧义见第八节 |
| FR-18 | 推荐入口：当前可用商品及近期热度 | 按项目背景提供简单热度推荐，复用统计结果；算法为工程约定，不扩展为机器学习系统 |

订单状态处理、单价筛选和简单推荐的具体口径属于工程约定，不将其表述为老师逐字规定的接口或算法。

## 4. 本工程业务规则

### 4.1 商品、单价与订单金额

BR-01：在老师给定 items 字段基础上增加 price，类型采用 DECIMAL(10,2)，表示商品当前单价。金额使用十进制计算与存储，单价必须大于零，不用浮点数推算成交金额。

BR-02：首版每单一件商品，orders.amount 保存下单时读取并确认的单价。创建订单的输入不允许调用方任意指定最终金额。商品由 100.00 元改为 120.00 元后，原有 100.00 元订单仍保持 100.00 元，新订单记录 120.00 元。

BR-03：仅状态正常的用户可以下单，仅在售商品可以被购买。账号或商品不存在、已停用、已下架时不生成订单。下单失败后不能留下半成品订单。

BR-04：订单状态约定为 0 待处理、1 已完成、2 已取消；允许待处理转已完成或已取消，不允许已完成和已取消相互覆盖。普通用户可取消本人待处理订单，完成订单由管理员处理。月度成交金额仅统计已完成订单。

### 4.2 分类、档案与删除

BR-05：根分类 parent_id 为 NULL；其他分类的上级必须存在。分类不能指向自身或自己的后代。有子分类或商品引用时拒绝删除，须先调整关联关系。

BR-06：商品必须关联一个存在的分类。商品状态约定为 1 在售、0 下架。未被订单引用的商品可删除；已被订单引用的商品保留基础记录，使用下架维持历史订单关联。

BR-07：每个用户维护一份档案，profiles.user_id 采用唯一约束；这是工程约定，原文仅规定外键。账号日常使用停用处理，避免破坏订单等历史引用。

BR-08：评论评分为 1 到 5，文字内容不得为空。普通用户仅能修改、删除自己的评论；管理员可按管理权限处理。商品详情按“一商品一份详情”组织，MongoDB item_details.item_id 建唯一索引。

### 4.3 查询、日志与跨库结果

BR-09：分页参数必须为正整数；结果按固定字段排序。月份统计时间范围为当月第一天起、下月第一天之前；金额统计排除待处理和已取消订单。

BR-10：MySQL 商品和用户编号以统一的 64 位整数表示，MongoDB 关联字段采用兼容整数类型，不混用字符串编号。基础记录存在但详情暂缺时应明确提示，不伪造详情或无声丢弃商品。

BR-11：MySQL 事务仅保证参与该事务的 MySQL 操作。MongoDB 写入失败时须返回可识别结果，保留重试或修复依据；不能把一次 MySQL commit 描述为两库同时提交。商品详情未保存完整时不向用户显示为已完成录入并可正常购买。

BR-12：浏览、登录及业务操作记录按时间保存，日志不记录明文密码。热门口径为所选时间范围内浏览次数；用户报告的统计范围应随结果显示。

## 5. 数据范围与数据库分工

### 5.1 MySQL

MySQL 保存具有明确关系和约束的基础业务数据。老师列明五张表，现有五张表继续使用；不重新初始化 MySQL 数据目录。

| 表 | 业务含义 | 主要关联或工程补充 |
|---|---|---|
| users | 用户、登录凭据哈希、角色及状态 | 用户名与邮箱唯一 |
| categories | 分类及上下级 | parent_id 自引用外键，可为空 |
| items | 商品名称、分类、状态、创建和更新时间 | category_id 外键；新增 price 单价 |
| orders | 用户、商品、订单金额、状态和时间 | user_id、item_id 外键；amount 为历史金额 |
| profiles | 用户档案 | user_id 外键；按工程约定加唯一约束 |

必须显式声明主外键，为高频查询设计索引；至少 2 个视图、2 个存储过程、2 个触发器，每张表至少 10 条测试数据。过程、触发器应服务实际业务，并在设计与测试阶段确定具体职责，不只凑数量。

### 5.2 MongoDB

MongoDB 保存商品扩展详情、评论和日志，体现嵌套对象与数组的用途，而不是简单复制关系表。

| 集合 | 内容 | 结构重点 |
|---|---|---|
| item_details | 商品说明、图片、扩展属性 | images 数组、metadata 嵌套对象，item_id 关联 MySQL |
| comments | 用户与商品、文字、评分、标签和时间 | tags 数组，user_id、item_id 关联业务记录 |
| action_logs | 浏览等行为及访问时长、客户端信息 | client_info 嵌套对象及时间字段 |
| system_logs | 登录、系统与业务操作记录 | action_detail 嵌套对象及日志等级 |

至少 4 个集合，每集合至少 20 条测试文档；原文另有“日志类100+”，本工程准备让两类日志各达到 100 条以上，以覆盖该要求。至少实现 3 个真实聚合管道，分别覆盖评论统计、热门排行和用户活动报告，并为高频查询建立索引。

## 6. 技术与质量要求

| 项目 | 课程要求与实施原则 |
|---|---|
| 开发环境 | Java，JDK 17+、Maven 3.8+、MySQL 8.0+、MongoDB 5.0+；使用 IntelliJ IDEA 或 Eclipse |
| 数据访问 | DAO 模式划分 MySQL 与 MongoDB 访问；MySQL 使用 JDBC、HikariCP，MongoDB 使用 MongoClient |
| SQL 执行 | Java 执行的 SQL 全部使用 PreparedStatement，严禁字符串拼接 SQL |
| 事务 | 创建订单等使用 JDBC 显式事务；验证成功提交及失败回滚的实际结果 |
| 密码与权限 | BCrypt 或同类密码哈希；角色与本人数据权限在业务层验证 |
| 配置与异常 | 连接信息放 properties/yml；真实密码不提交仓库；统一自定义异常及可理解提示 |
| 应用日志 | SLF4J + Logback；与 MongoDB 业务日志分别验证，不把终端打印当作 MongoDB 已写入 |
| 自动化验证 | JUnit 5；覆盖关键正常、边界、失败和权限行为，构建成功不能代替测试通过 |
| 性能 | 基于明确数据量、查询和运行条件分析索引及性能，报告优化前后真实结果；原文无固定延迟或并发阈值 |
| 版本管理 | Git + Gitee，main 可运行，完整 README 和 .gitignore；全程至少 11 次提交，前 11 天每天至少 1 次，信息采用 [Day XX] 功能描述 |

当前已验证 JDK 21、通过 Maven Wrapper 运行 Maven 3.9.16、MySQL 8.4.13 及本机 18306 端口连接。MongoDB 8.0.34与独立前后端已运行验证。VS Code可用于查看和编辑工程，IDE选用要求仍按老师原文单独核对。
